# P2.0 — паттерн выноса строк из Kotlin

Это рабочая инструкция для P2, не описание выпущенной версии. Базовая локаль `values` — zh; новые ключи добавляются в `values/strings_l10n.xml`, `values-en/strings_l10n.xml`, `values-ru/strings_l10n.xml`. Существующие `strings.xml` не переписывать. Ключ: `l10n_<area>_<meaning>`; в каждой локали один и тот же ключ и одинаковые форматные аргументы. Сначала проверить фактический путь от строки до экрана, ошибки либо модели.

## Примеры из текущего кода

- Compose: `ui/features/help/screens/HelpScreen.kt:105` вызывает `stringResource(R.string.help_loading_message)` непосредственно при построении `Text`. Аналогично заменять литералы `Text("…")` и `contentDescription` в composable; для аргументов использовать позиционные `%1$s` и `stringResource(R.string.l10n_..., value)`. Не вызывать `stringResource` из обычной функции или callback: вычислять в composable, затем передавать готовый текст.
- Сервис с `Context`: `services/CloudEmbeddingService.kt:54,80` формирует `CloudEmbeddingException(context.getString(R.string.memory_embedding_error_config_incomplete))` и параметризованное сообщение через `context.getString(R.string.memory_embedding_error_http, response.code, detail)`. Вынесенный текст получать через уже имеющийся `context` в точке создания результата, не сохранять готовый перевод глобально.
- ViewModel с `Context`: `ui/recovery/DataRecoveryViewModel.kt:23,56,70` уже хранит `Context` и создает сообщения состояния через `context.getString(R.string.data_recovery_sql_empty)` и `context.getString(R.string.data_recovery_query_completed, result.rows.size)`. В `State` оставить готовый текст, не вводить `Context` в data class и не протаскивать его через несколько слоев ради одной строки.

В контекстно-независимом `object`, модели или фоновой функции сначала проследить потребителя. Если текст исключительно UI, переводить на границе UI; если сообщение формируется в инструменте и нужен `Context`, исследовать существующий путь его передачи. Без установленного паттерна отметить `needs_decision` в `l10n/questions.md`, а не внедрять глобальный `Context` или новую цепочку выбора языка.

Исходную китайскую строку переносить байт-в-байт по смысловому значению (с учетом XML-экранирования), en/ru переводить по `l10n/glossary.md`; интерполяцию Kotlin `$value`/`${value}` переводить в `%1$s` с сохранением порядка и типа аргументов. Проверять Android-экранирование `\n`, `\'`, `\"`, XML-разметку и плейсхолдеры. Не трогать комментарии, логи, функциональные ключи/regex/названия приложений (D5), бинарные ассеты. Не писать обходных и резервных цепочек локализации.

## Сообщения JS-пакетов

По принятой политике D11 пользовательские сообщения на китайском выводятся для `zh`, на русском — для `ru`, на английском — для остальных кодов, включая нераспознанный системный тег. Сравнивать базовый код из строкового `getLang()` в момент формирования результата; у модуля QuickJS есть кэш экземпляров между вызовами (`JsExecutionScriptBuilder.kt`), поэтому нельзя вычислять перевод при создании экспортируемой функции и хранить его в замыкании. Для статических подписей, передаваемых обёртке, передавать функции, вызываемые в момент успешного или ошибочного результата, как в `assets/packages/tavily.js`.

Исходный `zh`-шаблон сохранять дословно. Если три шаблона интерполируют динамический результат с побочными эффектами, получить его один раз перед вызовом выбора языка; не размножать существующее выражение обработки ошибки. Не трогать `METADATA` с готовыми `zh/en/ru`, имена полей API, примеры входных данных, регулярные выражения и строки распознавания чужих страниц. `node --check` проверяет синтаксис, но не исполнение в QuickJS или переключение языка.

## Инвентарь и очередность

Исходный `l10n/inventory.json` содержит 19 498 записей в 1 253 файлах: `comment` 14 954, `log` 1 841, `literal` 2 702, `other` 1. Из 2 703 кандидатов `literal`/`other` грубая классификация только по пути: P2.A UI/services — 330 в 40 файлах; P2.B/C data/api/core/tools/util — 453 в 50; P2.D core/config/Prompt — 1 053 в 5; P2.C assets — 775 в 32; P2.E terminal — 80 в 8; прочие — 12 в 5. Это верхние оценки, а не число подлежащих переводу строк: подсчет захватывает функциональные данные и промпты; каждый литерал проверять по использованию, не переводить механически. Класс `other` — regex `12306.js:412` (функциональный, D5).

- A: экранные подписи, сообщения сервисов, accessibility и диалоги; первый ограниченный срез — `ui/features/settings/screens/ModelConfigScreen.kt`, только явно пользовательские литералы, включая `:1112,1167,1188,1231,1249,1450,1523,1663`. Строки логирования `:344,522,536` не менять; данные об именах правил `:1070–1082` проверить по потребителю до перевода.
- B: ошибки инструментов и данные, доходящие до пользователя/модели; отдельно проверить китайские имена приложений в `core/tools/defaultTool/standard/StandardUITools.kt:64–132` как D5, прежде чем трогать сообщения этого файла.
- C/D/E: функциональные значения исключить; ассеты после Kotlin, промпты — по решению D8 (английский для ru и указание отвечать на языке пользователя), `terminal` править в собственном репозитории подмодуля.

Каждая исполнительская партия — не более 12 файлов; состав утверждает архитектор после проверки путей использования. Проверка без сборки: просмотр `git diff --stat` и `git diff --check`, точное соответствие трех файлов ресурсов, выборочная проверка форматных вызовов и изменение инвентаря по `scan_cjk.py --diff`. Сборку/тесты запускать только по отдельному прямому запросу владельца согласно `AGENTS.md`; отсутствие сборки явно отражать в приемке.
